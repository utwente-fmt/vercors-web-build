VerCors Tutorial

Try VerCors Online

In PVL, a class can describe a thread by defining a run block. After constructing an object of such a class, the object represents a thread that is ready to run. The thread can then be started with fork and waited for with join.

This page explains the basic thread lifecycle first, and then shows how the same concepts combine with permissions, loops, and locks.

Thread classes and run blocks

The intuition behind a thread class is that each object stores the data that its thread will use, while the run block stores the code that is executed when the thread starts.

The syntax is:

class Worker {
    run {
        // Code executed by the thread
    }
}
Language for VerCors: pvl





The run block is not called like an ordinary method. Instead, it is started by forking an object of the class.


A run block can have a contract, just like a method. Its precondition describes the resources that must be available when the thread is started. Its postcondition describes the resources and facts that are returned when the thread has finished and is joined.





class Worker {
    int result;

    ensures Perm(result, write) ** idle(this);
    constructor() {
        result = 0;
    }

    requires Perm(result, write);
    ensures Perm(result, write) ** result == 1;
    run {
        result = 1;
    }
}


Language for VerCors: pvl









The constructor postcondition contains idle(this). This states that after construction the newly created object is an idle thread object, ready to be forked.


idle and running


Thread objects have a verification state. The two basic states are idle(t) and running(t).


The lifecycle is:


idle --[fork]--> running --[join]--> idle



The expression idle(t) states that thread object t is not currently running. A freshly constructed object of a class with a run block starts in this state, provided the constructor establishes idle(this).


The expression running(t) states that thread object t has been forked and has not yet been joined.


For example:





class ThreadObject {
    ensures idle(this);
    constructor() {
    }

    run {
    }

    void testLifecycle() {
        ThreadObject t = new ThreadObject();
        assert idle(t);

        fork t;
        assert running(t);

        join t;
        assert idle(t);
    }
}


Language for VerCors: pvl









These state predicates are resources. This matters because they are consumed and produced by fork and join: after fork t; you no longer have idle(t), and after join t; you no longer have running(t).


fork


The fork statement starts an idle thread object.


The syntax is:


fork t;



Here t must be an expression that points to a thread object. To verify fork t;, VerCors must know that t is idle and that the precondition of t’s run block holds.


When the fork succeeds, the thread becomes running. The resources required by the run block are transferred to the running thread.





class Worker {
    int result;

    ensures Perm(result, write) ** idle(this);
    constructor() {
        result = 0;
    }

    requires Perm(result, write);
    ensures Perm(result, write) ** result == 1;
    run {
        result = 1;
    }
}

void startWorker() {
    Worker w = new Worker();

    assert idle(w);
    fork w;
    assert running(w);
}


Language for VerCors: pvl









Forking an already running thread is rejected. After the first fork the object is running, so it is not idle anymore.





class Worker {
    run {
    }

    void forkTwice() {
        Worker w = new Worker();
        fork w;
        fork w; // Fails: w is running, not idle.
    }
}


Language for VerCors: pvl









join


The join statement waits until a running thread has finished.


The syntax is:


join t;



To verify join t;, VerCors must know that t is running. After the join, the thread is idle again, and the postcondition of the run block becomes available to the joining thread.


Continuing the previous worker example:





class Worker {
    int result;

    ensures Perm(result, write) ** idle(this);
    constructor() {
        result = 0;
    }

    requires Perm(result, write);
    ensures Perm(result, write) ** result == 1;
    run {
        result = 1;
    }
}

void startAndJoinWorker() {
    Worker w = new Worker();

    fork w;
    join w;

    assert idle(w);
    assert Perm(w.result, write) ** w.result == 1;
}


Language for VerCors: pvl









Joining a thread that is not running is rejected. For example, a newly created thread object is idle, so it cannot be joined before it is forked.





class Worker {
    run {
    }

    void joinBeforeFork() {
        Worker w = new Worker();
        join w; // Fails: w is idle, not running.
    }
}


Language for VerCors: pvl









Once a thread has been joined, it is idle again. This means the same thread object can be forked again, as long as the next fork can again satisfy the run precondition.





class Worker {
    ensures idle(this);
    constructor() {
    }

    run {
    }

    void reuseThreadObject() {
        Worker w = new Worker();

        fork w;
        join w;

        assert idle(w);

        fork w;
        join w;

        assert idle(w);
    }
}


Language for VerCors: pvl









Passing permissions to a thread


The contract of a run block is the main way to specify which heap locations a thread may use.


The intuition is the same as for ordinary method contracts:


    

  • The requires clauses describe what must be given to the thread at fork.
    • 

  • The ensures clauses describe what comes back at join.
    • 



While the thread is running, the joining thread should not rely on resources that were transferred to the forked thread. Those resources are available again only after join.


The following example uses two thread objects to update different fields of the same Point. Because one thread receives permission for p.x and the other receives permission for p.y, the two updates are independent.





class Point {
    int x;
    int y;
}

class UpdateX {
    Point p;
    int oldX;

    requires Perm(this.p, 1\3) ** Perm(this.p.x, 1) **
             Perm(oldX, read) ** oldX == this.p.x;
    ensures Perm(oldX, read);
    ensures Perm(this.p, 1\3) ** PointsTo(this.p.x, write, oldX + 1);
    run {
        Point q = this.p;
        q.x = q.x + 1;
    }
}

class UpdateY {
    Point p;
    int oldY;

    requires Perm(this.p, 1\3) ** Perm(this.p.y, 1) **
             Perm(oldY, read) ** oldY == this.p.y;
    ensures Perm(oldY, read);
    ensures Perm(this.p, 1\3) ** PointsTo(this.p.y, write, oldY + 1);
    run {
        Point q = this.p;
        q.y = q.y + 1;
    }
}

void updatePoint() {
    Point p = new Point();
    p.x = 2;
    p.y = 6;

    UpdateX updateX = new UpdateX();
    updateX.p = p;
    updateX.oldX = p.x;
    fork updateX;

    UpdateY updateY = new UpdateY();
    updateY.p = p;
    updateY.oldY = p.y;
    fork updateY;

    join updateX;
    join updateY;

    assert PointsTo(p.x, write, 3) ** PointsTo(p.y, write, 7);
}


Language for VerCors: pvl









The auxiliary fields oldX and oldY store the values that each thread promises to increment. This is useful because \old is currently not supported in postconditions of run blocks.


Forking and joining several threads


For a fixed number of threads, fork each object and then join each running object.





class Worker {
    int result;

    ensures Perm(result, write) ** idle(this);
    constructor() {
        result = 0;
    }

    requires Perm(result, write);
    ensures Perm(result, write) ** result == 1;
    run {
        result = 1;
    }
}

void twoWorkers() {
    Worker w1 = new Worker();
    Worker w2 = new Worker();

    fork w1;
    fork w2;

    assert running(w1) ** running(w2);

    join w1;
    join w2;

    assert idle(w1) ** idle(w2);
    assert w1.result == 1 ** w2.result == 1;
}


Language for VerCors: pvl









When the number of threads is determined by a collection, loop invariants must describe which thread objects are idle, which are running, and which permissions are still available.


The following pattern first constructs idle thread objects, then forks them all, and finally joins them all.





class NodeThread {
    int val;

    ensures Perm(val, write) ** idle(this);
    constructor(int v) {
        val = v;
    }

    run {
    }
}

void forkJoinLoop(seq<int> nodes) {
    seq<NodeThread> threads = seq<NodeThread> {};

    loop_invariant 0 <= i && i <= |nodes|;
    loop_invariant |threads| == i;
    loop_invariant (\forall int j=0..|threads|, int k=0..|threads|; threads[j] == threads[k] ==> j == k);
    loop_invariant (\forall* int j=0..|threads|; idle(threads[j]));
    loop_invariant (\forall* int j=0..|threads|; Perm(threads[j].val, write));
    for (int i = 0; i < |nodes|; i++) {
        NodeThread node = new NodeThread(nodes[i]);
        threads = threads + [node];
        assert idle(threads[i]);
    }

    loop_invariant 0 <= i && i <= |nodes|;
    loop_invariant (\forall int j=0..|threads|, int k=0..|threads|; threads[j] == threads[k] ==> j == k);
    loop_invariant (\forall* int j=i..|threads|; idle(threads[j]));
    loop_invariant (\forall* int j=0..i; running(threads[j]));
    loop_invariant (\forall* int j=0..|threads|; Perm(threads[j].val, write));
    for (int i = 0; i < |nodes|; i++) {
        fork threads[i];
    }

    loop_invariant 0 <= i && i <= |nodes|;
    loop_invariant |threads| == |nodes|;
    loop_invariant (\forall* int j=i..|threads|; running(threads[j]));
    loop_invariant (\forall* int j=0..i; idle(threads[j]));
    for (int i = 0; i < |nodes|; i++) {
        join threads[i];
    }
}


Language for VerCors: pvl









The distinctness invariant is important: it tells VerCors that two different indices do not refer to the same thread object. Without this, permissions such as idle(threads[j]) and running(threads[j]) may accidentally describe the same object through different indices.


Returning computed results


Fork/join threads are useful when the result of a computation is stored in fields and collected after joining.


For example, the following thread recursively computes a Fibonacci number. Each non-base case creates two child thread objects, forks both, joins both, and then combines their output fields.





decreases n;
pure int fib(int n) = n < 2 ? 1 : fib(n - 1) + fib(n - 2);

class Fib {
    int input;
    int output;

    requires Perm(input, 1\10) ** Perm(output, write);
    ensures Perm(input, 1\10) ** Perm(output, write) ** output == fib(input);
    run {
        if (input < 2) {
            output = 1;
        } else {
            Fib f1 = new Fib(input - 1);
            Fib f2 = new Fib(input - 2);

            fork f1;
            fork f2;
            join f1;
            join f2;

            output = f1.output + f2.output;
        }
    }

    ensures Perm(input, write) ** Perm(output, write) ** input == n;
    ensures idle(this);
    constructor(int n) {
        input = n;
    }
}


Language for VerCors: pvl









The constructor provides ownership of the fields and establishes idle(this). The run contract then specifies that after joining a Fib thread, its output field contains fib(input).


Sharing state with locks


If multiple threads need to access the same field, they cannot all receive write permission for that field directly. Instead, put the shared permission in a synchronization object, such as a lock invariant, and let each thread acquire the lock before touching the shared state.


The syntax and details of locks are explained in Atomics and Locks. In a fork/join program, the important idea is that the shared object is committed before it is given to the threads, and each thread’s run block requires enough information to lock it.





lock_invariant Perm(x, write);
class Counter {
    int x;

    ensures committed(this);
    constructor() {
        x = 0;
        commit this;
    }

    requires committed(this);
    void main() {
        CounterWorker w1 = new CounterWorker(this);
        CounterWorker w2 = new CounterWorker(this);

        fork w1;
        fork w2;
        join w1;
        join w2;
    }
}

class CounterWorker {
    Counter counter;

    ensures Value(counter) ** counter == c ** idle(this);
    constructor(Counter c) {
        counter = c;
    }

    context Value(counter) ** counter != null ** committed(counter);
    run {
        lock counter;
        counter.x = counter.x + 1;
        unlock counter;
    }
}


Language for VerCors: pvl









The workers do not own counter.x directly. The permission for x is stored in the lock invariant of Counter. Each worker temporarily obtains that permission between lock counter; and unlock counter;, and must restore the invariant before unlocking.


Common mistakes


The thread lifecycle is linear: each fork must start from an idle thread state, and each join must start from a running thread state.


Typical mistakes are:


    

  • Forking the same object twice without a join in between.
    • 

  • Joining an object that has not been forked.
    • 

  • Forgetting to establish idle(this) in the constructor of a thread class.
    • 

  • Forgetting to provide the resources required by the run precondition before fork.
    • 

  • Trying to use resources in the parent thread while those resources have been transferred to a running thread.
    • 

  • Sharing write permission for the same field between threads directly, instead of using disjoint permissions or a synchronization mechanism such as a lock.
    • 



As a rule of thumb, write the lifecycle facts explicitly in the surrounding contracts and loop invariants: use idle(t) for threads that may still be forked, running(t) for threads that must still be joined, and the run contract for the resources transferred between the two states.
