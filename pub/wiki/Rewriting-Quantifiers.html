VerCors Tutorial

Try VerCors Online

The underlying verification tools on which VerCors relies, such as Viper and the automatic theorem prover Z3, do not allow logical or arithmetic operators in quantifier triggers.[^1] However, a verification condition is often most naturally expressed using these operators, and a trigger involving them may be the only suitable choice. In some cases, a quantifier can be rewritten into an equivalent expression with suitable triggers. This section explains which patterns VerCors can automatically rewrite for you.[^2]

[^1] This restriction has good reasons. Suppose that + were allowed in triggers and that you chose f(x+5) as a trigger for ∀ x; 0<=x && x<10; {:f(x+5):}>0. The trigger would fire for f(1+5), because it can match the expression syntactically. However, it would not fire for f(5+1) or f(6), which could lead to unexpected results for users.

[^2] The paper Scalable Deductive Verification of Data-Level Parallel Programs explains some of the rewrite patterns and formal proofs for these patterns.

![Note] Contracts for parallel blocks and GPU kernels are automatically quantified over the parallel threads. For example, writing context xs[blockIdx.x*blockDim.x + threadIdx.x] in a CUDA kernel contract results in context (∀ int blockIdx.x=0..gridDim.x, int threadIdx.x=0..blockDim.x; xs[blockIdx.x*blockDim.x + threadIdx.x]);. The most reasonable trigger here is xs[blockIdx.x*blockDim.x + threadIdx.x], but this expression needs to be rewritten before it is accepted as a trigger. Automatic rewriting is therefore often useful for parallel constructs in VerCors.

Linear (Nested) Quantifiers

An access pattern such as xs[j*5+i] often occurs in programs processing flattened multidimensional arrays. For instance, the following code sums a multidimensional array.

int sum = 0;
for(int j=0; j<n; j++)
  for(int i=0; i<5; i++)
    sum += xs[j*5+i]

The outer loop would need permission to read from xs, which could be expressed as the following.

loop_invariant (∀ int i, int j; 0 <= i && i < 5 && 0<= j && j < n;
  Perm(xs[j*5+i], read));

This is equivalent to the following quantifier.

loop_invariant (∀ int ij; 0 <= ij && ij < 5*n; Perm(xs[ij], read));

Thus, when xs[j*5+i] is given as the trigger (that is, {:xs[j*5+i]:}) for the quantifier above, VerCors automatically rewrites the quantifier and uses xs[ij] as the new trigger.

In general, VerCors can rewrite a multidimensional quantifier into a one-dimensional quantifier with a suitable trigger if the pattern in the trigger is injective. For the quantifier above, the pattern j*5+i is injective: different valid values of i and j never access the same element of xs.

General pattern

The most general pattern that VerCors supports for this rewrite is as follows:

f(x_1, ..., x_n) = a_1*x_1 + ... a_n*x_n + b;

where the inlined function f is then used as follows:

(∀ int x_1, ..., int x_n; C(x_1, ..., x_n); 
  R({:A(f(x_1, ..., x_n)):}, (x_1, ..., x_n)));

Here, x_1, … x_n are the quantified variables, and C(x_1, ..., x_n) represents their domain. It can be viewed as an inlined Boolean function that expresses the precise constraints on x_1, … x_n. R is the resulting condition or resource that the quantifier expresses; it accesses some A^[3] in a specific manner.

[^3] A can be an array, but also functions and other data structures.

VerCors will try to rewrite this towards the following

(∀ int x; Y(x); R({:A(x):}, f_inv(x)));

provided that the access is injective. In that case, VerCors finds the inverse function of f, written here as f_inv, and a new domain Y. A[x] is then used as the trigger. VerCors can prove that the access is injective if the following conditions hold:

  1. Each x_i has an inclusive lower bound, denoted by x_min_i.
  2. All strides (the a_i) are non-zero.
  3. All a_i have the same sign.
  4. The stride of x_{i+1}, namely a_{i+1}, is greater than the maximum contribution of the lower dimensions. More precisely, every i < n:
abs(a_1)*(x_1-x_min_1) + ... + abs(a_i)*(x_i-x_min_i) < abs(a_{i+1})

Here, abs denotes the absolute value.

For more details on this precise procedure, and a machine checked proof, we refer to the paper Scalable Deductive Verification of Data-Level Parallel Programs.

![Caution] If the pattern is completely general (that is, the a_i do not resolve to concrete numbers), VerCors may run into problems with non-linear arithmetic. This is not due to the rewriting itself; it is because the given pattern is already non-linear.

Multiple patterns

The procedure above also works when multiple patterns are present. For example, in the following quantifier, the function g has two patterns as arguments: j*5+i and h-4.

(∀ int i, int j, int h; 0 <= i && i < 5 && 0<= j && j < n && h>=0 && h<2; 
 {:g(j*5+i, h-4):});

Thus, it is rewritten to the following equivalent quantifier:

(∀ int ij, int h; 0 <= ij && ij < 5*n && h>=-4 && h<-2; 
 {:g(ij, h):});

However, each pattern must be independent; that is, patterns cannot refer to the same quantified variables.

Other Rewrites

VerCors also automatically rewrites a quantifier containing arithmetic when it already has one pattern that is suitable as a trigger. It introduces a new quantified variable for this purpose. For example, in the following quantifier, the first argument to g has i as its pattern, which is a valid trigger. Therefore, other arguments containing i can be replaced.

(∀ int i; i>0; {:g(i, i+1):});

This is rewritten as follows, since we can introduce a new quantified variable for the expression i+1.

(∀ int i, int j; i>0 && j==i+1; g(i, j));

This can be combined with the rewriting of linear quantifiers above if needed.

Alternatives to rewriting linear patterns

Instead of automatically rewriting patterns, you can also replace the arithmetic with helper functions. So long as you use the exact helper functions, you can use these to trigger the quantifiers correctly.

For instance, you can replace the above example with helper functions for + and *:

pure int plus(int a, int b) = a + b;
pure int mul(int a, int b) = a * b;

...
loop_invariant (∀ int i, int j; 0 <= i && i < 5 && 0<= j && j < n;
  Perm({:xs[plus(mul(j,5),i)]:}, read));
...

Or alternatively, make an index function as follows.

pure int idx(int a, int b) = 5*a+b;
...
loop_invariant (∀ int i, int j; 0 <= i && i < 5 && 0<= j && j < n;
  Perm({:xs[idx(a,b)]:}, read));
...

![Caution] Remember that the quantifiers only get triggered on syntactical equivalence. Thus even if xs[plus(i, mul(j,5))] is semantically equivalent to xs[plus(mul(j,5), i)], only the latter will trigger the quantifier.
